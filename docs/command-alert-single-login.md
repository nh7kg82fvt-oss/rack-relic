# Command login and the email setup check

The private Preview's **Email alert setup check** uses the existing Rack Command password and remembered HttpOnly cookie session. It does not create a second account, request another email link, or place provider tokens in browser storage. An expired remembered cookie is refreshed once per request; subsequent private checks verify that renewed JWT and the same current database session without reusing the old refresh cookie. A signed-out page visit returns only to the fixed `/api/command-center` entry. No arbitrary return URL is accepted.

The page checks only the original fictional owner-alert delivery after the owner reviews the current setup. Opening the page, signing in, following a link and refreshing never send an email. The same current owner session is checked before and after a manual operation, in setup verification, and immediately before any existing transport email POST. The server ignores browser bearer-token headers for this entry. Revoked sessions, an unavailable session reader and cached or late authentication results keep the operation closed.

Leaving the alert page clears the entered review and any displayed delivery result. Blur, hidden visibility and pagehide abort pending browser work; returning by focus, visibility or back/forward restoration first checks the current server session and starts with an empty review. A late response cannot restore the former result or overwrite a newer checked session. Missing lifecycle listeners or unavailable signal storage leave the controls disabled.

The Command logout button emits only a denial notification before its asynchronous sign-out starts. The fixed same-origin localStorage marker and same-window event contain a version, signed-out action and random nonce, with no owner/session IDs, tokens or records. Alert pages receiving that marker immediately clear and do not refresh while sign-out may still be pending. Notifications never grant access, revoke cookies or send email. A delayed or malformed marker can only hide information; later foreground or manual refresh must obtain fresh server authorization. Browser events can be delayed or missed in frozen or stopped contexts, and blocked storage or unavailable randomUUID can prevent a cross-tab marker; fresh server session checks remain the authority.

The existing one-fixture worker, sender, Resend transport, message text, request hash, journal and delivery receipts remain unchanged. The original delivered test must be preserved. The page does not establish live alerts, background processing, continuous case monitoring or owner-read evidence. It changes no provider setting, database function, activation flag, credential, recipient or financial control.

The Command company cards explicitly show Resend and GitHub as unverified here. Refreshing Command does not check either provider. The email setup link is a same-origin manual check, not a live Alerts service.

A future alert template may contain only the fixed read link `/api/command-center#cases-heading`, using the known Preview origin when an absolute URL is needed. This is a generic cases section, not proof that an older case has a supported deep link. A future template must be separately versioned and reviewed before new operational alerts are accepted; changing the current email body would change its immutable request hash. No email body or existing intent is changed in this update. A link must never carry a token, personal data, arbitrary return URL or financial action.
