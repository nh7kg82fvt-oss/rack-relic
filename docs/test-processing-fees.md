# Original charge fee evidence

The private test operator can load a saved fee record or refresh it from Stripe. Refresh makes authenticated GET requests to verify the configured test account, succeeded PaymentIntent, captured platform Charge and its BalanceTransaction. Order identity, gross amount, USD currency, fee components and the gross-minus-fee net must agree. Missing balance evidence, stale/cached responses, currency conversion, destination/connected-account charges and contradictory fee components fail closed. No percentage-based estimate is used.

The tenth isolated-test migration, `20261031_charge_fee_evidence.sql`, stores one immutable record per paid order with unique charge and balance identities. It checks participant ownership and fresh evidence, rejects conflicting updates, uses the existing catalog/order lock order and grants execution only to service_role. It adds no browser table grants. The server separately verifies the existing explicit test operator and both test refund flags on every request. GET reads saved evidence; POST accepts only an order reference and refreshes evidence without writing to Stripe.

This is original-charge evidence, not completed fee allocation or a seller payout balance. A refunded charge can retain its original processing fee. Refund fees, standalone/invoiced provider fees, credits, tax settlement and any seller recovery remain separate reconciliation work. No ledger entry, job state, inventory state, transfer, payout or label changes here. The displayed original charge net must never be used directly as a transfer amount.

Local validation covers PostgreSQL permissions and identities, concurrent repeats, immutable evidence, refunded charges, provider-only GET traffic, cached/mismatched responses, fee component totals, HTTP input bounds, operator isolation and browser sign-out races. Deployment verification and the actual provider record are tracked in the private completion checkpoint. Public checkout and live money movement remain closed.
