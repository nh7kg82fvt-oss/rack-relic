# Private informational sample tracking

This workflow reads the already-saved successful sample transaction using authenticated Shippo GET requests. It does not register external tracking numbers, buy labels, attach a webhook, claim a real shipment was delivered or release seller funds. Shippo documents the latest label status on the Transaction object's `tracking_status` field: https://docs.goshippo.com/tracking/tracking .

The exact private preview branch and existing operator configuration are required. `RACK_RELIC_TEST_TRACKING_ENABLED` defaults to off. The browser supplies only an order reference. Fresh operator membership and participant access precede the provider read and are checked again before storing it. The request/rate/transaction metadata, test mode and saved tracking number must all match the successful private sample. Provider prose, customer addresses, document URLs and credentials are not exposed in the tracking response.

Apply `20261031_tracking_observations.sql` only to isolated staging after the sample-label migration. It adds two private RLS tables and two backend-only RPCs. Browser roles have no table or RPC grants. Every distinct provider observation is retained; repeated observations deduplicate without growing the history. The last checked time advances on repeated fresh reads. Older checks and older dated carrier events cannot overwrite the current status. Terminal regressions, conflicting same-time events and missing timestamps on changed dated statuses require review; the accepted status is preserved. Review is sticky. No ledger, inventory, order-risk or fulfillment-job changes occur.

Both legacy string tracking statuses and dated object statuses are accepted. Missing timezone information is rejected instead of guessing a carrier event time. A sample transaction can legitimately remain UNKNOWN forever; sample labels are not real shipments. Provider-issued deterministic mock scenarios use carrier `shippo` and `SHIPPO_*` tracking numbers and must never be attached to an unrelated order's real sample transaction.

Live tracking, authenticated webhook handling, delivery evidence and seller settlement remain separate launch requirements. Shippo's HMAC webhook configuration requires its account/solutions team; see https://docs.goshippo.com/tracking/webhook-security . Any later webhook should be treated as a wake-up hint and reconciled against authenticated provider data before changing operational state. This manual test view does not activate a webhook or weaken signature requirements.
