# Owner-operated fictional practice proposal

This package is source only, unpublished, uninstalled and OFF. It does not open payments or verify a real seller. No account, key, provider request, SQL installation or setting change follows from construction or a passing local test.

The owner remains the actual authenticated Rack Command owner. A trusted private binding identifies the fixed fictional catalog target; it is not a second seller login. The identifiers can legitimately be equal. The public template contains no actual private user/fixture identifier.

## Entry points

- Rack Command keeps its existing login, work controls and `form-action 'none'` policy. After a fresh owner overview, the optional boolean `ownerFixtureSetupAvailable: true` permits an owner-only link. Missing/false is unavailable or unknown, not provider health.
- `GET /api/closed-practice-seller/begin` independently verifies the current owner and session, then renders a confirmation. It reads only Auth/current-session evidence. It performs no seller-context, provider, account or readiness operation.
- The confirmation uses a native same-origin form POST with the literal body `action=begin`. It creates at most the original fictional account after the existing durable claim permits it, saves the returned account binding, and emits its validated setup link only as a confidential 303 Location to the same owner response. No application JSON, browser storage or application log receives that link.
- Exact raw `GET /api/test-marketplace` is the passive owner return page. Returning from Stripe confirms no readiness. Only explicit native POST `action=observe` reads current setup and records its scoped observation; `action=refresh` creates a fresh link for the original known account.

When the independent feature selects the acceptance environment, exact GET `?action=config` and `?action=orders` retain the existing closed reader. A sole nonempty raw `?code=` value retains the historical email/Command PKCE flow; that historical Auth exchange is separate from the new passive return and operation budget. Existing exact `?view=cancel` and `?view=return&session_id=cs_test_...` URLs delegate unchanged and prove no payment completion. Unknown, encoded, duplicate, reordered or mixed aliases hold before the legacy shell. The separate legacy environment delegates entirely unchanged. OFF retains existing behavior.

## Configuration and authority

All new construction inputs default NULL/OFF. Future setup would require separate review of `RACK_RELIC_OWNER_PRACTICE_ENABLED`, a sealed `RACK_RELIC_OWNER_PRACTICE_BINDING` with exact version/mode/owner/fixture/finite window, and a dedicated restricted clean-TEST `RACK_RELIC_OWNER_PRACTICE_STRIPE_KEY`. None is configured or authorized by this package. The existing modern server and publishable credentials remain opaque server inputs. No value is discovered, printed or copied by this source review.

An explicit existing acceptance `RACK_RELIC_TEST_CHECKOUT_ENABLED === 'true'` conflicts with this closed rehearsal. It keeps strict owner routing selected but leaves the owner runtime OFF/404 and availability false, preventing legacy financial fallthrough. Historical reviewed GET routes retain their existing behavior; no actual setting is changed.

The binding is no more than one hour and must match the exact existing acceptance tuple and configured owner. Published Command selection currently expects historical refund flag strings; the package supplies those strings only inside its isolated owner-session composition. It never changes the original environment, financial flags, checkout handler or refund runtime. This compatibility applies to the standalone owner-practice composition only; the main Command route retains its existing historical refund-flag selection requirements. Local availability proves construction and an unexpired binding only, not installed SQL, credential permissions, provider readiness or owner authorization for an action.

The SQL proposal at `supabase/test/20261113_owner_practice_seller.sql` keeps owner, fixture and window function constants NULL. It adds only a service-only public invoker and fixed-search-path private dispatcher, with four literal branches: context, claim, save, protection. It uses the installed current-owner helper and existing seller functions, adds no direct Auth/table grants and no correlation table, and never borrows the Tax guard. The exact private body/window/binding and future access need their own review before use.

The fresh request UUID binds each response to the owner/session/token expiry/fixture/operation, but is correlation rather than durable nonce consumption. The existing seller prepared-to-dispatched claim is the sole creation barrier. A lost claim acknowledgment holds before provider POST; an unknown create/save outcome never grants a replacement. Only the original known account can be refreshed.

## Timing, browser and acceptance limits

The original at-most-five-second wall and monotonic scope begins when the handler starts its operation scope, after synchronous route/header checks. It does not measure Vercel arrival or time spent in an upstream router. All new API exports use `bodyParser: false`; actual hosting must preserve the raw stream and avoid preconsumption. Raw streams/strings reject encoded or duplicate action fields exactly. The defensive pre-parsed object path can validate only one decoded action and cannot prove that a host did not normalize earlier raw bytes.

The scope fences body consumption, fresh current-owner checks, RPC/provider response streams, service JSON, retained async continuations and the final response. It does not undo or prove the timing of a remote SQL/provider commit after abort. SQL has its own finite observation; pre/post STABLE session reads do not linearize concurrent revocation. An existing server credential can have broader power than this client boundary.

The real Node response must support `getHeader`, `removeHeader` and `destroy`. Expiry after an unsent Location clears that header before a generic held response; cleanup failure destroys the connection. Both new originating form documents permit only self and the exact validated `https://accounts.stripe.com` form destination. A separate local synthetic Chrome probe demonstrated that self-only form policy blocked a cross-origin 303 and permitting the exact synthetic destination allowed it. This is local browser evidence, not actual hosted/Stripe acceptance. Command's `form-action 'none'` remains unchanged. Actual host header/logging/custody behavior, authenticated owner/nonowner/revocation flows, raw-body routing, private key permissions, installed policy, provider wire headers and native cross-origin 303 browser navigation remain unaccepted. Local Node/PGlite/fictional HTTP checks prove source behavior only, not native PostgreSQL, provider or hosted acceptance.

All payment, Tax, shipping, agreement, financial release, real seller verification, backup/global restore and operational launch gates remain held. The new seller return callback never automatically performs seller/provider/readiness actions; the preserved historical email/PKCE Auth exchange is described above. No new principal is needed for the owner-operated design, and the preserved Website/testing and CCP workflows remain separate.
